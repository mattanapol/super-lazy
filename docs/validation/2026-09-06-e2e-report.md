## Step 6 — Prove a gate blocks a premature completion claim

superpowers alone, because completion would still rest on a claim rather

### Why `CHECK:` carries the resolved path and not the variable

The same two ledgers were written in the two rejected forms and run, because
the choice between them is load-bearing and was not obvious:

| `CHECK:` form | Authoring session | Fresh-shell `--reverify` |
|---|---|---|
| `node "${CLAUDE_PLUGIN_ROOT}/scripts/gate-lint.mjs" …` | `FAIL`, exit 1 | `FAIL`, exit 1 |
| `node "$LEDGER/scripts/gate-lint.mjs" …` | **`ALL MET`, exit 0** | `FAIL`, exit 1 |
| `node "/Users/kaewsai/repos/temp2/scripts/gate-lint.mjs" …` | `ALL MET`, exit 0 | `ALL MET`, exit 0 |

Both failing forms fail identically, with
`Error: Cannot find module '/scripts/gate-lint.mjs'` — the empty expansion C1
described. The variable form is the more dangerous of the two precisely
because it *passes first*: the author sees `ALL MET`, and the demotion only
surfaces later, in someone else's shell, as
`UNMET: 1 (met: 0, reran: 1, previously met reverified: 1)`. `references/SECURITY.md`
confirms why: an approval binds the exact command text and the inherited
`PATH`, not arbitrary environment variables, so nothing revalidates that the
variable still means what it meant at approval time.

That is the evidence behind the rule now stated in `skills/verifying/SKILL.md`:
`$LEDGER` is for the interactive commands an agent types; a `CHECK:` gets the
resolved absolute path written out.

`--approve` left approval-cache records in the user's global
`~/.unlazy/approved/` store; they are inert now that the working directories
they bind no longer exist.
